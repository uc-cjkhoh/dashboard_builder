# Decisions — custom SQL on a card

Continues [decisions-platform.md](decisions-platform.md). This file holds D105 (Edit SQL), the one place the server accepts SQL text, D106 (MySQL syntax in it), D128 (the data preview after Save), D130 (the preview's light grid and resizable columns) and D131 (its pages). Edit an entry in place when it changes.

### D105 — Edit SQL: free-text SELECT on a Data Source card, the one exception to rules 2 and 3
**Edit SQL** in a Data Source card's ☰ menu (a right-click menu until 2026-11-16, a pencil icon button left of the title until 2026-11-17, [D129](decisions-relationships.md#d129--a-cards-actions-sit-in-one--menu)) opens a dialog on the card's default `SELECT` (every column of its table). **Save** makes the card read the user's own query: its columns become what the query returns, and every worksheet query that reads that table reads the query instead.
- **Why:** Tableau's *Custom SQL* lets a user pick the columns or reshape a table by editing its query. Doing the same with pickers would mean rebuilding SQL in the UI; a beginner who can write a `SELECT` is better served by writing it.
- **The exception:** until now the server never accepted SQL text ([D1](decisions-platform.md#d1--read-only-against-clickhouse), [D6](decisions-platform.md#d6--identifiers-validated-against-the-live-catalog--backtick-quoted), rules 2–3). This is the one endpoint shape that does. The text is **not** built from identifiers and is not parameterised: it is the user's own statement, run with their own ClickHouse account.
- **What still holds** (all server-side, `ClickHouse/CustomSql.cs`): exactly one statement starting `SELECT` or `WITH`, ≤ 10,000 characters, comments stripped, no `;`, balanced brackets (so it cannot leave its wrapper), no `SETTINGS` clause (so `readonly=2` and the time limit cannot be changed), and no table function that reads outside ClickHouse's own tables (`url`, `file`, `s3`, `remote`, `mysql`, …). The text is embedded only as a derived table, `FROM (…) AS t0`, inside the same bounded query as ever: `readonly=2`, the 12 s time limit, the `LIMIT`, whitelisted aggregations, bound filter values. Nothing can run but a read.
- **Columns:** `DESCRIBE TABLE (query)` on every read (reads no rows); a duplicate or more than 200 columns is a 400. Every field a worksheet names must be one of them (same unknown-identifier path as a table).
- **Errors are echoed:** ClickHouse's own words for a query problem (syntax, unknown column or table, wrong types, no access — codes 27, 36, 42–44, 46–48, 53, 60, 62, 81, 215, 386, 497) reach the dialog as a 400 on `source.sql`, cut at "(version" and the stack trace, one line, ≤ 400 characters, because "failed at position 8" is what a person needs to fix the query. Every other failure stays a generic upstream error (the rule in [D6](decisions-platform.md#d6--identifiers-validated-against-the-live-catalog--backtick-quoted) about never echoing messages); credentials never appear in a query error.
- **Shape:** the card stays an ordinary table card (`entity.customSql`, not `entity.source`), so it can be related and joined. A query carries `sources: [{ kind: "sql", db, name: table, sql }]` and the server reads that derived table wherever the query names the table (base or join side; `QueryRequest.Sources`). Rejected: a new `source` kind like union / unpivot — it takes no joins, which would have made Edit SQL unusable on any card with a relationship.
- **Relationships:** a new query must keep every column the card's relationships use (the dialog says which ones); the key columns' types are not re-checked.
- **Reads over a custom-SQL card:** profile, View data, the histogram and the relationship suggestion send the card's `source` (kind `sql`, for that very table) and read the query as a derived table; columns, filters and key kinds are validated against what the query returns ([api-custom-sql.md](../reference/api-custom-sql.md#reads-over-a-custom-sql-card)). Saving a new query that changes a relationship key to a kind its partner cannot be related to is refused (so is going back to the table — **Reset to default** + **Save** — when it would do the same). A union or unpivot card has no SQL to edit and still refuses View data, the histogram and the join check.
- **Editor and live checking:** the dialog is a code editor (CodeMirror 5 and sql-formatter, vendored like ECharts — [sql-editor.md](../concepts/data-source/sql-editor.md)). While you type, instant client-side checks mirror the guard, and once they are clean ClickHouse describes the query 0.8 s after the last keystroke (aborted and replaced by every newer one). That is one `DESCRIBE` per pause, reading no rows, on the user's own connection; it is the price of showing ClickHouse's verdict before Save. Rejected: a heavier editor needing a build step (CodeMirror 6, Monaco), and a hand-written highlighter over a text area (no folding or bracket matching without rebuilding an editor).
- **Saved** in the workbook as `customSql` on the entity; an invalid saved value is dropped with an issue and the card reads its table again.
- **Rejected:** a structured column picker only (no free text) — safer but not what was asked; a separate "custom query" card beside the table — the user chose to replace the card's columns in place.
- Detail: [query-sources.md](../concepts/data-source/query-sources.md#custom-sql-on-a-card), [api.md § Custom SQL](../reference/api-custom-sql.md).

### D106 — MySQL syntax in Edit SQL, translated to ClickHouse
The Edit SQL dialog has a footer switch **MySQL | ClickHouse**. **MySQL is the default**; ClickHouse stays the main syntax: it is what the card always runs, and what a saved query is stored as.
- **Why:** many users know only MySQL, and the database is ClickHouse. Translating on the way lets them write what they know, and the panel "ClickHouse SQL that will run" shows what actually runs.
- **Translator: sqlglot (Python), vendored in `Tools/vendor`, run as a child `python3 -I` process by `SqlTranslator`** behind `POST /api/sql/translate`. The user asked for an existing "mysql-to-clickhouse compiler or API". Evaluated: **sqlglot** — mature, 30+ dialects, ~6 MB of pure Python, 0.1–0.4 s per call; **`@polyglot-sql/sdk`** (a Rust port as WebAssembly) — runs in the browser but ships a 28.5 MB `.wasm`; **a hosted API** — rejected outright: every query would leave the network; **a hand-written translator** — would cover only the common cases. Vendoring means the host needs only Python 3 (3.9 is there), no `pip install`, no root, and the service user is the one that installed it. Without Python the MySQL option is switched off and nothing else breaks.
- **ClickHouse is authoritative.** Save stores the ClickHouse query (`customSql`) and, when it was written in MySQL, that text beside it (`customSqlMysql`) so reopening shows exactly it. A query written in ClickHouse and shown as MySQL is a best-effort display.
- **No guesswork on a round trip.** A case-sensitive comparison comes back ignoring case, and ClickHouse text MySQL has no form for (`toDate`, `uniq`, arrays, lambdas, `PREWHERE` …) is refused by name on the way to MySQL rather than shown as look-alike text (sqlglot would print `TODATE(x)`). The dialog remembers paired texts, so switching back and **Save without editing** return exactly the original. A query written in ClickHouse opens in MySQL syntax only if the way back reports no meaning-changing repair (`changes`), ClickHouse accepts it with the same columns, and `EXPLAIN SYNTAX` reads both texts the same way; otherwise it opens in ClickHouse syntax with a warning. A false alarm costs only that; a missed change would silently alter the rows returned. Measured: 11 of 27 typical queries open in ClickHouse syntax (a string comparison, a division, a ClickHouse-only function; `currentDatabase()` is a known false alarm) — see [sql-syntax.md](../concepts/data-source/sql-syntax.md#the-round-trip-check).
- **Strict where it can be:** sqlglot runs with `ErrorLevel.RAISE`, so a construct it knows has no equivalent is refused; the converted text goes through the same `CustomSql` guard as any custom SQL before it is described or saved. No new way to run anything: the script only converts text, reads nothing, opens no connection. One thing needs types, `col = col` between two text columns (MySQL ignores case, ClickHouse does not): the script lists each such pair, and **`SqlController` asks ClickHouse to `DESCRIBE`** a probe (`SELECT l AS l, r AS r FROM` the same FROM / JOINs; guarded by `CustomSql.Clean` like any custom SQL, no rows read, at most 6) and calls the script again with the pairs to fold. So the translate endpoint now reads column types from the connection (it already needed one); a failed probe leaves the comparison as written. The same probes tell whether a plain `GROUP BY` / `ORDER BY` / `DISTINCT` column is text, and then only a note is added (no rewrite: the values shown would change).
- **Repaired where sqlglot's plain output would run but mean something else** (found by feeding it about 50 queries): `DATEDIFF` → `dateDiff('day', b, a)` (a − b, ClickHouse's start/end order); `TIMESTAMPDIFF` → `age('unit', a, b)` for day to year and elapsed seconds (`intDiv(dateDiff('second', a, b), 3600)`) for hours, minutes and seconds (whole units, as MySQL counts — plain `dateDiff` counts boundaries, a silent wrong answer, and **`age('hour')` is wrong on the 26.8 test server**, found by probing it); `DATE_ADD` / `DATE_SUB` → `d ± INTERVAL n unit` with a numeric `n`; `LIKE` → `ILIKE` (MySQL's default collation ignores case). A text comparison (`= 'abc'`, `!=`, `IN`) is rewritten to `lowerUTF8(toString(x)) = lowerUTF8('abc')` so it ignores case as MySQL's does (an earlier version only warned; the user asked for the fix). The cost is stated in a note that never blocks Save: it can be slower on very large tables (no primary-key use) and accents still differ. Column-to-column comparisons (a join on text), number- and date-like literals, `''`, mixed lists and subqueries are left alone (still case-sensitive), and ClickHouse syntax keeps the exact comparison. Division by zero is NULL (`DIV` is wrapped like `/` and `%`). **`||` is refused**, not translated: it is `OR` in MySQL's default mode and concatenation in ClickHouse, so either guess is silently wrong for someone. Anything without a faithful form is refused with the reason. **Tier 2 (loud failures) was then worked through, each construct checked on the server:** compound intervals (`YEAR_MONTH`, `DAY_*`, `HOUR_*`, `MINUTE_SECOND`) become **one** interval of months or seconds, because MySQL adds the whole value at once (Feb 29 + `'1-2'` is Apr 29; adding a year then two months gives Apr 28); a column as an interval amount becomes `toIntervalUnit(col)`; `TIMESTAMPDIFF(MICROSECOND)` works; date-like text operands are wrapped in `toDate` / `toDateTime`; `STR_TO_DATE` (`parseDateTimeOrNull`, a Date or a DateTime), `UNIX_TIMESTAMP`, `LAST_DAY`, the three JSON scalar forms (text, number, boolean, null and a missing key apart), `LIKE … ESCAPE` (the escape character rewritten to backslashes), the dropped clauses (`SQL_CALC_FOUND_ROWS`, hints, `STRAIGHT_JOIN` as a join kind, `FOR UPDATE` with a note) and `@var` / `@@var` refused at their position. **A defect in what shipped was found on the way:** sqlglot rewrites MySQL date-format codes into another style, so `DATE_FORMAT(d, '%H:%i')` came out as `'%H:%M'`, and ClickHouse's `%M` is the **month name** — minutes printed as "March", silently. ClickHouse's own `formatDateTime` is MySQL-style, so the original codes are kept (a parser subclass keeps `DATE_FORMAT`, `STR_TO_DATE`, `FROM_UNIXTIME` and `TIME_FORMAT` as plain calls) and only the codes that print differently are rebuilt. The earlier docs called `DATE_FORMAT` "converted correctly"; it had never been run on the server. A review also found `JSON_EXTRACT` / `->` returning `''` instead of NULL for a missing key (fixed with `JSONHas`); the script now silences sqlglot's stderr and the server drains it, so a chatty run cannot stall the pipe. `DESCRIBE TABLE (subquery)` and 16 end-to-end translations were **run on the test server (ClickHouse 26.8.36.3)** and match MySQL's documented results; they were run by hand, so another ClickHouse version could differ.
- **Honest limits:** it is a translator, not a guarantee — several MySQL-only features still pass through unchanged and ClickHouse may refuse them. The full list is in [sql-syntax.md § Limitations](../concepts/data-source/sql-syntax.md#limitations).
- Detail: [sql-syntax.md](../concepts/data-source/sql-syntax.md).

### D128 — Saving Edit SQL shows the card's rows in the data preview
The Data Source has a data preview docked under the canvas: the first 100 rows of one card ([canvas.md § Data preview](../concepts/data-source/canvas.md#data-preview)). **Preview data** in a card's ☰ menu opens it ([D129](decisions-relationships.md#d129--a-cards-actions-sit-in-one--menu)), and **Save** in Edit SQL opens it on that card as well. If it already shows that card, it re-reads.
- **Why:** the Edit SQL dialog's live check describes the query; it reads no rows. Users who change a card's SQL want to see that the data changed as they meant, and the column list alone can't show that.
- **How:** no new endpoint. `POST /api/rows` already takes the card's custom SQL as `source` (D105), and a union or unpivot card reads `/api/union` / `/api/unpivot`. The panel is a sibling of the canvas ground, not a dialog, so the model stays in view beside the rows.
- **Rejected:** opening the rows dialog over the model (it hides the card being checked and must be closed before the next edit); a row grid inside each card (cards would grow, and links and free slots depend on card size); leaving the preview closed after Save (the user would have to find the button for the most common check).

### D130 — The data preview is a light grid with resizable columns
The Data Source's data preview draws the shared rows table lighter and lets each column be resized from its header's right border ([canvas.md § Data preview](../concepts/data-source/canvas.md#data-preview)). Asked for 2026-11-17: drag-to-resize columns, and a table that is less visually heavy.
- **What changed (this panel only):** one-line headers, highlighted with a `--surface-3` fill and bold names (asked for the same day; the type moves to the tooltip and screen-reader text; the card above already lists it); hairline rows with zebra stripes (every second row `--surface-2`, asked for the same day to tell rows apart; the row under the pointer tints `--surface-3`); a 1px line between columns from header to last row, so each column is plainly its own (asked for the same day); columns as wide as their content (48–320px) instead of stretched across the panel; numbers right-aligned with tabular figures after the first column.
- **Resize:** the same feel and bounds as a worksheet table's column handles — drag, ← / → in 8px steps (Shift × 5), double-click or Delete for automatic, 48–600px — so columns resize one way across the app. Widths are session view state per card and column name, never in the workbook (no schema change for a preview).
- **Rejected:** restyling the shared `.rows-table` everywhere (the rows dialog and View data were not asked about, and the dialog's stripes help across its wider rows); keeping the type as a second header line (it doubled the header's height for what the card already shows); right-aligning a numeric first column (it pulls the row's first value off the 16px gutter under the title); saving widths in the workbook.

### D131 — The data preview pages 100 rows at a time
The Data Source's data preview shows the first 100 rows of a card, with **‹ Page [n] ›** to step to the next or previous 100, or to type a page number and go straight there (1–1,001; asked for the same day) ([canvas.md § Data preview](../concepts/data-source/canvas.md#data-preview)). Asked for 2026-11-17.
- **How:** `POST /api/rows` and `/api/unpivot` take an optional `offset`, 0–100,000 (`MaxRowsOffset`), validated on both sides and never clamped (golden rule 3); the reads stay `LIMIT`-bounded and read-only. A request without it is unchanged, so every other caller reads as before.
- **Stable pages:** a read with no `ORDER BY` returns rows in whichever order ClickHouse's threads finish, so `OFFSET` alone could repeat or skip rows between pages. A paged read of a stored table or unpivot is run on one thread (`SETTINGS max_threads = 1`, at the end of the whole statement), which reads the table's parts in order; page 1 is read the same way, so page 2 starts where it ended. A server that takes no settings (`QueryGuards.None`) gets the offset alone. Custom SQL is read as written: its own `ORDER BY` decides its page order (a single thread would slow a heavy query for no guarantee). Rows can shift if the table changes between pages.
- **Unions don't page:** a union's read splits its limit across its tables (`UnionShare`: each table gets an even share), so it has no single row order; its pager is hidden and it keeps its first 100 rows.
- **Cap:** the last page starts at row 100,000 — the same order of size as the CSV export cap ([D24](decisions-platform.md#d24--showing-all-data-bounded-requests-paging-other-date-grouping)); a preview is for looking, a worksheet or export for reading everything.
- **Rejected:** clamping a typed page to the last one (golden rule 3: out of range is refused with a message); `ORDER BY` every column (a full sort of a large table per page); ordering by the table's sorting key (not every engine or card has one, and custom SQL has none); a total row count and "Page n of N" (a `count()` per page change, expensive for custom SQL; not asked for); infinite scroll (the panel is short, and pages make "where am I" plain).
