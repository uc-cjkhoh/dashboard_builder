# Decisions — the Marks card against Tableau

Lookup: [README.md](README.md). The comparison itself: [tableau-marks-comparison.md](../reference/tableau-marks-comparison.md). Edit an entry in place when it changes.

## D118 — The Marks card follows Tableau except where the app has no uploads, no maps or no contrast rule yet

- **Chosen:** the Marks card matches Tableau's Marks-card help (Color, Size, Label, Detail, Tooltip, Shape, Path) wherever the job can be done with the app's own parts. Where it cannot, it differs on purpose and says so in the interface (a hint, never an error). The differences are listed in [tableau-marks-comparison.md](../reference/tableau-marks-comparison.md); each one is either backlog work or one of the three reasons below.
- **No uploads → no custom shape palettes.** Tableau's Shape card loads image files from a repository folder. The app takes no file uploads and stores specifications only ([out-of-scope.md](../development/backlog/out-of-scope.md)), so Shape keeps seven built-in symbols and per-sheet member shapes (D115). A user-supplied image would also need the stored-colour contrast and size rules.
- **No maps → no halos and no Polygon.** Both exist in Tableau for map and background-image views; they come back with the maps item ([analytics-and-maps.md](../development/backlog/analytics-and-maps.md)).
- **No stored-colour contrast rule yet → no free palette editing.** Custom hex colours and an editable palette wait for a written contrast and saturation rule for stored colours (the palette entry in [charts-and-formatting.md](../development/backlog/charts-and-formatting.md)). Until then colour choices are tokens and 24 fixed swatches.
- **Not a Tableau clone:** where the same job is done differently, the app keeps its own control (Label position, Automatic colour scale, per-line tooltip styling). A feature is added to close a gap only when a backlog entry says so.
- **Rejected:** copying Tableau's dialogs one for one (it would add controls that do nothing on these chart types, against the gating rule of [D108–D117](decisions-dashboards.md)); treating the comparison as a to-do list (the backlog is the only to-do list).

## D119 — Line pattern and Line markers on the Marks card

- **Chosen:** Path flyout → **Line pattern** (Solid, Dashed, Dotted) and Color flyout → **Line markers** (Automatic, All, None) on Line, Area and Combo lines, in the Tableau Marks card's own words. Both are stored on `format` only when they differ from the default (`linePattern` `dashed` | `dotted`; `lineMarkers` `all` | `none`), so older workbooks open unchanged and a sheet that never set them draws byte for byte as before; an unknown saved value is dropped and reported, never clamped. One pure rule serves the drawing and the panel (`line-style-model.js`, `line-marker-model.js`), so a control is offered exactly where it does something and otherwise **disabled with its reason as the title**.
- **A dash that already means something keeps its meaning.**
  - A measure cue (a colour measure beside several measures) names its line: the cue wins and Line pattern is disabled with that reason. The cue's markers likewise win over None.
  - A comparison line stays dashed and faded; beside a Dashed or Dotted main line it takes a dash-dot, so the two differ without colour.
  - Reference lines and bands are analytics, never patterned. The trend line stays dotted, but beside a Dotted main line it takes the same dash-dot as a comparison line (it also has its end label), so the two differ by more than colour.
- **A straight line whose thickness follows Size stays solid, as in Tableau** (a dash cannot vary in thickness): the thickness is drawn as polygons (D108). The bound is 2,000 points in all the lines together; the drawing records the count it drew per sheet (`noteLinePoints`) and the panel reads it, so both apply the same `lineSizeMode`. Past the bound, and on a stepped line or an area, Size sizes the markers, so Line pattern applies there.
- **None never hides a value.**
  - A lone value (no neighbour on either side: a one-point line, a point between gaps) keeps its dot.
  - A mark that carries a label keeps a clear anchor: the dot is filled and bordered `transparent`, not given opacity 0, which a label sitting on it would inherit (seen in the browser check). Hover restores the dot's own fill and border, and the series' mark opacity still applies.
  - A marker that is data stays: Size on a stepped line, an area, or a straight line past 2,000 points (D108) and a measure's cue marker win over None, and Line markers is disabled with that reason. A sheet never drawn counts as within the bound.
  - The tooltip and the axis pointer are unchanged.
- **Marker size and Marker shape are not disabled under None:** a lone value and a hover dot still use them. The Line markers control's title says what None does to them.
- **All** pins every dot (`showAllSymbol`), because ECharts otherwise thins dense symbols, and a big canvas chart skips LTTB sampling for it (sampling would drop points and their markers; the 5,000-group cap bounds the cost). Automatic is untouched, including its own gap (a lone value past 60 points shows no dot).
- **Selected points (Tableau)** is built as [D124](#d124--line-markers-selected-dots-only-at-the-click-selected-marks).
- **Rejected:** a custom polygon drawing for dashed thickness; patterning the cue lines (it would erase what names each measure); hiding the controls instead of disabling them (the user could not learn why); storing the defaults (every saved workbook would change).

## D120 — Edit Sizes: Sizes vary and a typed start and end value

- **Chosen:** the From zero checkbox becomes a **Sizes vary** drop-down (Automatic, By range, From zero), and a measure gets an optional typed **Start value** and **End value**, as in Tableau's Edit Sizes dialog. Stored as `format.sizeScale` `vary` (`"range"` / `"zero"`), `start`, `end`, only when set.
- **Automatic is today's per-chart default, not Tableau's data-driven rule.** Tableau picks From zero when the data does not cross zero. D110 could make the colour scale's Automatic data-driven because new sheets start with `auto` in `defaultFormat`, while an absent value still reads sequential. `sizeScale` stays off `defaultFormat` ([D108](decisions-dashboards.md#d108--size-a-dimension-steps-marks-edit-sizes-a-lines-own-thickness-text-size-and-size-beside-a-colour-split)): a sheet without it round-trips unchanged and every saved sheet's absent setting already means the chart's own default (bubbles from zero, everything else by range). Adopting Tableau's rule would redraw those sheets, and it would make the sizes jump when refreshed data starts crossing zero. So Automatic stays the per-chart default and a data-driven rule is not built. An older file's `fromZero` boolean reads as the same mode (`true` = From zero, `false` = By range), is kept as saved on import, and loses to `vary` when both are present; the control writes `vary` and drops `fromZero`.
- **A typed end saturates, never hides.** A value below the start takes the smallest mark size and one above the end the largest (through Smallest / Largest and Reversed, so a reversed scale gives the below-start value the largest mark). All-equal data keeps full size and is never reversed unless an end is typed. A typed end replaces the bubble floor of 1. A start is not used where the span starts at zero (explicit From zero, or Automatic on a bubble chart): its control is disabled with that reason. Typed values apply to a measure only; beside a Size dimension they are ignored and disabled.
- **Reversed is off under an explicit From zero, as in Tableau.** The control is disabled with the reason, and picking From zero drops a stored Reversed and start. An older file holding both still draws reversed exactly as before (import keeps it); its checked, disabled Reversed says the reversal is still applied and that By range or Automatic turns it off. Reversed stays available under Automatic on bubbles, which are From zero by default, so no existing bubble chart loses it.
- **A start that does not apply is dropped, never left to block.** Where the span starts at zero (explicit From zero, or Automatic on a bubble chart) the Start field is off. Picking Automatic on bubbles, or typing an End there, drops a stored start; the drawing (`sizeEnds`) never lets such a start cross an End. The simpler alternative of validating against the hidden start was rejected: import cannot know the chart type, so a crossed pair would still be dropped whole at the next save.
- **Limits:** start and end are finite numbers within +/-1e12 (`SIZE_VALUE_LIMIT`), start below end. On import a non-number or out-of-range value is dropped and reported, a crossed pair drops both, a start beside From zero is dropped; nothing is clamped. The server never sees the setting (client-only).
- **The legend names the ends in words:** `Size: sum qty (10 to 50, set)`, `start set` or `end set` for one typed end; the legend shows the typed end, not the data's.
- **Rejected:** a Sizes vary choice for a dimension (its members are steps); Tableau's two checkboxes ("Start value in legend" / "End value for range") as separate switches (a blank field already means off).

## D121 — Tooltip behaviour: Show tooltips, command buttons, and Responsive or On hover

- **Chosen:** three Format controls on the charts that have a hover tooltip: **Show tooltips** (on by default), **Command buttons** (off by default) and **Tooltip mode** (Responsive by default, or On hover), in Tableau's words. Stored on `format` only when not the default (`showTooltips: false`, `tooltipButtons: true`, `tooltipMode: "hover"`), validated like the other format parts (an unknown value is dropped and reported on import, never coerced). Unset = the tooltip it always was: a golden fixture over 23 chart builders proves the option and the formatter output are identical.
- **Show tooltips off** removes the tooltip and the axis pointer on every chart type, applied once to the built option (`applyTooltipBehaviour`, so a dashboard widget obeys it too). A value is never only in a tooltip: data labels, the selection and its chip, View data and the table view stay, which is why switching the tooltip off is safe.
- **Command buttons** are Keep only, Exclude and View data, with the same effects as the selection chip: no filter logic was added. The tooltip is made enterable; because ECharts moves a tooltip with the pointer (so reaching it moves it, and on an axis tooltip crossing the next category swaps its content), it is anchored once per hovered mark a few pixels from where the pointer entered, and hides 400 ms after the pointer leaves. A real-mouse browser check shows the pointer reaching it on bar, line, point and pie.
  - Only where a click selects by a dimension value (`BUTTON_TYPES`: bar, stacked, line, area, combo, pie, donut, point), in the editor, on a mark with a real value (not Other, not NULL), and not under a drill hierarchy, a calculated or date-part first dimension, or a point chart split by Colour or Shape. A dashboard widget's marks cross-filter, which is not Keep only, so it gets none. Where they would do nothing the control is disabled and says why.
  - **A date axis the server groups has no buttons, and says so.** A temporal first field on a chart type that groups dates (`BUCKET_TYPES`) is bucketed by the server unless Group dates is Exact; a bucket is a period, which no filter value matches, so a click selects nothing there (`rc.bucketedKey === 0`). The Format gate decides what the sheet can: an explicit grain disables the control with the reason, Group dates → Auto keeps it with a note (the data decides, and Auto may leave a short range ungrouped). When the drawing drops the buttons for that reason it adds a one-line hint above the chart, the app's usual way to say why a mark channel is missing.
  - **Gantt is left out:** one row can hold several bars (colour members) and its tooltip index is a bar, not a row, so the tooltip cannot address a row the way its click does. It keeps its hover tooltip and click.
  - **Group Members and Create Set are not built:** the app has no sets, and a group needs a member list chosen first. **Allow selection by category** is not built either: a tooltip line would need to know which of its fields is a discrete dimension and select that one, a separate piece of work. Both stay in the backlog entry.
  - Buttons are `<button type="button">` with text (never colour alone), built from fixed labels and a whole-number mark index; the click is one delegated listener on the chart host reading `data-tt-cmd` and `data-tt-idx`. No inline handler, and no user text reaches the markup (a member named `<b onclick=x>` is escaped in the tooltip text). Keyboard and screen-reader users keep the same actions on the selection chip; the buttons are a pointer shortcut.
  - **Keep only and Exclude always set the action** rather than toggling it, so choosing one from a tooltip of an already selected mark does not clear it. **View data** reads the mark's rows without changing the selection.
- **Responsive and On hover.** On hover puts the buttons in every hover tooltip. Responsive keeps hover tooltips as today and **pins** the tooltip of the mark a click selects, with the buttons.
  - The pin is **one-shot**: the click leaves a transient mark (`takePin`) that the next drawing consumes, so a Format edit or returning to the tab never re-opens a tooltip, and nothing is saved in the workbook.
  - While pinned the tooltip uses `triggerOn: "none"` and `alwaysShowContent`, so hovering another mark neither replaces it nor leaves a button-less tooltip stuck on screen; other marks show no hover tooltip until it is dismissed. Dismiss: Esc, a click on empty chart, the same mark again (it deselects), the chip's clear, a command, or any redraw. ECharts ignores a hide while `alwaysShowContent` is set, so dismissing first gives the pin up and restores hover tooltips.
- **Known limits:** no touch behaviour (a tap selects and, in Responsive mode, pins; there is no hover); focus does not return to the chart when a pinned tooltip is dismissed (the tooltip has no keyboard focus to return from: the keyboard route is the selection chip); a pinned tooltip is not moved when the chart is resized (it stays where it was until dismissed).
- **Rejected:** pinning from the stored selection (it would re-open on every redraw); `hideDelay` alone (the pointer cannot reach a tooltip that follows it); a custom popover outside ECharts (it would duplicate every chart type's tooltip text); buttons on a dashboard widget (they would mean something different from the chip there).

## D122 — Include totals in the colour encoding

- **Chosen:** a per-measure **Include totals** check box in Format → Conditional formatting (Table and Text). Ticked, the measure's total cells (grand-total column, subtotal rows, grand-total row and the cells where they cross) take that measure's scale, bars and rules exactly as ordinary cells do, and the total values count when the scale's extent (and the auto diverging midpoint) is found. It is the app's place for Tableau's Edit Colors → Include totals: a crosstab's cells take a colour scale from Conditional formatting, not from the Colour slot.
- **Stored only while on:** `format.conditional[key].totals = true`. Off is absent, so an older file and every table that never ticks it draw byte-identically (a golden of every layout x setting x totals combination, generated from unmodified main, proves it). The flag is dropped when the measure stops drawing anything (Cells None, no rules), so no invisible value lingers; on import a non-boolean, and a true flag on an entry that draws nothing (Cells None, no rules), is dropped and reported, never coerced, and the rest of the entry stays.
- **Gate:** the box is disabled, with the reason as its tooltip and `aria-description` (the way the tooltip controls say why, D121; no extra text on every table's Format card), when: the measure's total has no value (average, median, distinct count, percentile or a table calculation: "A total of an average, median or distinct count has no value here"); Grand totals and Subtotals are both off ("Turn on Grand totals or Subtotals"); the layout draws no total ("No total is drawn in this layout": a grand-total column needs Columns dimensions, a grand-total row Rows dimensions, subtotals two Rows dimensions with the measures on top, `totalsDrawn`); or the measure has no scale, bars or rule. A saved "on" stays enabled (clearable) in the first three cases, with a visible note saying why nothing is coloured.
- **The key and the table tell the truth:** a measure counts as including totals only if at least one of its totals has a value, so the key says "Totals included" (or names the measures) only while a total of an included measure is really coloured, and a measure whose totals all read "—" is plain and unnamed even with a stale saved flag.
- **Which total values count:** exactly the ones the table shows. A total of a sum, count, min or max is that aggregation over the whole group, and is coloured like a cell. A total of an average, median or distinct count has no combined value in the browser (it would need the rows behind it), so it reads "—" today; a "—" is never coloured and adds nothing to the extent. A collapsed header's total while rows are still loading also reads "—". If those totals ever get a real value they will be coloured the same way: the colouring reads whatever the cell shows.
- **The extent widens, on purpose:** a grand total is larger than a single cell and compresses the scale, so ordinary cells look paler. The Format note says so ("Totals are larger than single cells, so cells may look pale") while a scale or bars are on, rather than hiding totals from the extent: Tableau counts them too. Choosing which totals count (grand only) was left out; the Grand totals / Subtotals switches decide which totals exist.
- **Look kept:** a total cell keeps `xt-total` (bold, surface tint, grand-total separator) and `num`; a scale tint is inline and wins over the total tint, and a rule's tone is repeated for `td.xt-total` so the total tint cannot outrank it. The ink is still picked for >= 4.5:1 (`contrast.js`); a rule keeps its icon, tooltip and key entry, so colour is never the only cue.
- **Partly loaded tables:** the app never receives a whole-result total row for a crosstab, so totals are those of the loaded rows exactly as shown; the key reads "Scales, bars and totals use the N rows loaded so far".
- **Print and CSV:** unchanged except colours (a CSV has none); the export reads values, not cells.
- **Rejected:** a separate totals scale (a total would not be comparable with cells); including totals by default (existing tables would change colour); a hidden control when totals are off (the user could not learn why it exists).

## D123 — Gantt bar size from Size: a measure sets each bar's thickness

- **Chosen:** a **Size measure on a Gantt sets each bar's thickness**, with the bar chart's own machinery ([D108](decisions-dashboards.md#d108--size-a-dimension-steps-marks-edit-sizes-a-lines-own-thickness-text-size-and-size-beside-a-colour-split), [D120](#d120--edit-sizes-sizes-vary-and-a-typed-start-and-end-value)): the value's share of the span (`measureShareFn`), shaped by Size flyout → Edit Sizes (Smallest / Largest %, Sizes vary, a typed Start / End value, Reversed), then `barThickness`. The Size measure rides along as a third measure after the start and the length and never becomes the start, the length or the end. No new stored key: `format.sizeScale` is reused, so a saved workbook is unchanged and a stored setting with no Size drawn has no effect.
- **Thickness range:** 6 px at the smallest value up to **80 % of the bar's row slot** at the largest (the bar rule of D108; never under 6 px, also in a slot narrower than 6 px). The fixed thickness of a Gantt without Size (60 % of the slot, at most 28 px) is untouched, so a Gantt without Size draws byte for byte as before (a golden of eight cases at two slot heights, generated from unmodified main, proves it). The 28 px cap is **not** applied to a sized bar: in a tall pane with few rows the largest bar is wider than an unsized one (as a bar chart's is); Size flyout → Edit Sizes → Largest size (%) lowers it. A row slot is at least 24 px, so with many rows the range is 6 to 19 px.
- **The span is the drawn bars' own.** A row skipped for a bad start or length (counted in the notice) is not in the span, so the legend ("Size: qty (3 to 27)") and the thickness agree with what is on screen. All equal, or one bar, is the largest thickness; negative values span the range; a **missing (NULL) Size draws the thinnest visible bar** (6 px), never hides the row, and has no Size line in the tooltip.
- **A Colour split:** each (row, member) bar takes its own cell's thickness on one scale across every member, as D108 does for split bars. A Gantt does not offset members side by side (bars of one row sit on its line, as before), so where two members' bars overlap in time the **thinner bar is drawn above** (`z2` of 1000 minus the thickness, set on the drawn rectangle and its length label: ECharts ignores `z2` on a custom item's group, so a thick later member would otherwise hide a thin earlier one), keeping both visible. The tooltip names the member and carries the Size line.
- **A Size dimension stays a hint**, now worded for the Gantt ("A field on Size by member doesn't apply to a Gantt — it draws one bar per row, which a member step would split"): a dimension is one more group-by, which would split the one-bar-per-row layout (a row would become several bars). It adds no group-by (`sizeDimensionOf` stays null for a Gantt), the bars keep their one thickness, the hint shows above the chart and on the Size tool's editor, and Edit Sizes is not offered.
- **Edit Sizes is offered while a Size measure is drawn on a Gantt:** `gantt` joins `SIZE_SCALE_TYPES`, and `sizeChannel("gantt", n)` is ok for a measure only with exactly two measures on the shelf (a Gantt with any other count draws a hint, not bars, so Edit Sizes is not offered). Sizes vary Automatic means By range, as on bars.
- **Not adopted: length from Size.** In Tableau a Gantt's bar length is usually also set by a measure on Size. Here the length comes from the second measure or Format → Length = End ([D104](decisions-dashboards.md#d104--a-gantt-takes-its-end-from-a-field-splits-by-colour-and-is-a-click-target)): it is explicit, works with date starts (a length in days) and needs no second meaning for Size. Size is the Marks-card channel for how big a mark is drawn, which is thickness.
- **Saved sheets draw differently, their data does not change:** a saved Gantt that already had a Size measure (ignored before; the measure was fetched and unused) now draws sized bars and the Size legend.
- **Limits:** the row slot is not widened for Size: the chart-fit slot is 24 px per row, so with many rows the sized range is narrow (6 px up to about 80 % of what the pane leaves each row), and the Size line's 24 px takes a little from every slot. The Size legend sits at the top right under the Gantt's own legend: many Colour members that wrap the legend onto a second line, or a very long Size name, can run into it. Where Colour members overlap in time, the length label of a shorter bar is drawn over the longer bars of its row. A PNG / SVG / print export reads the same drawn chart.
- **Rejected:** a thickness cap of 28 px (it would flatten the range in a tall pane); scaling over every row including skipped ones (the legend would name values with no bar); offsetting split members side by side (a different layout, not asked for); a Size dimension as steps (splits the row).

## D124 — Line markers: Selected, dots only at the click-selected marks

- **Chosen:** Color flyout → **Line markers** gains **Selected** (stored `lineMarkers: "selected"`; the order is Automatic, Selected, All, None), as in Tableau's Marks card. A dot shows only at the **selected marks**: every series' point at a selected category (as Label marks → Selected does), on Line, Area and the lines of a Combo. The selected marks are the click selection on the primary dimension: the worksheet's own (`sheet.selection`) in the editor, the board's cross-filter selection on a dashboard's source widget (`rc.selected`) — the same selected-mark model Label marks → Selected reads.
- **Passed on its own.** `lineMarkersSpec` in `render-cartesian.js` hands the chart the selected indices (`selectedMarks`) whenever Line markers is Selected, on both cartesian render paths (the series chart and the colour split), whatever Label marks is set to. Label marks' own hand-over (`labelMarksSpec`) is unchanged: with both set, labels follow Label marks and dots follow Line markers. Selecting or clearing redraws the chart as it already did.
- **No selection means no markers; a lone value keeps its dot** (D119: a data value never becomes invisible). Selected is None's plan with the selected points added to what stays visible: once any dot is kept (a selected point or a lone value) every other point is a clear item (filled and bordered `transparent`, back in the mark's colour on hover); when nothing is kept, no dot exists at all unless a label needs an anchor, in which case every point is clear. On a long line (past 60 points, where Automatic shows none) the selected points get their dot the same way (`showAllSymbol`, so ECharts does not thin them), as D116 does for labelled marks.
- **A mark can still be clicked with no dot drawn.** Seen in the browser check, with real mouse clicks: under None and under Selected with nothing selected, no symbol is drawn, yet a click on a point selects it, because moving the mouse over it makes ECharts draw its hover symbol and the click lands on that. Hover still shows the point's dot and the tooltip (axis pointer). So Selected needs no extra clickable dots.
- **A marker that is data wins, as under None:** Size on a stepped line, an area or a straight line past 2,000 points, and a measure's cue marker, keep every marker; the control is **disabled, reads All and says why**.
- **Selected does nothing wherever a click cannot select a mark, so it says so** (the same rules as the tooltip's command buttons, [D121](#d121--tooltip-behaviour-show-tooltips-command-buttons-and-responsive-or-on-hover); `selectGate`, `selectDrawnReason` in `line-marker-model.js`, the click's own rules in `selectHandler`). Known from the sheet, the **Selected choice is disabled with the reason** while Automatic, All and None stay usable (a disabled control would block them): no dimension, a calculated dimension (no column to filter on), an active drill hierarchy (a click steps down), a date part, an explicit Group dates grain (a mark is a period). A stored Selected there keeps showing and the control's title says why. Group dates: Auto is the default and the server decides, so the choice stays available with a note, and the chart carries a hint above it when the data was grouped (`lineMarkersSpec` returns a `note`, joined to the Marks hints on both render paths: dates grouped into periods, with Group dates → Exact as the way out). On a dashboard widget, a drill hierarchy still selects, and a field with a data type cast cannot start a cross-filter: that hint says so. A read-only view says nothing, since a selection can still arrive from another widget.
- **Title:** the control's title says "no selection = no markers" and that a lone point keeps its marker.
- **A big canvas chart skips LTTB sampling for Selected, as for All** (sampling could drop the selected point and its dot; the 5,000-group cap bounds the cost).
- **Exports read the selection at export time:** the PNG and SVG come from the same chart instance, so an export shows the dots of whatever is selected then.
- **Stored only when chosen:** `lineMarkers` `selected` is a new allowed value (`LINE_MARKERS`); an unknown value is still dropped and reported, and an older file, or one with Automatic, All or None, builds exactly the option it built before (a fixture generated from the code before this change proves it).
- **Rejected:** coupling the dots to Label marks (it would make Line markers depend on an unrelated setting and on labels being drawn); drawing a transparent dot on every point so a mark can be clicked (not needed: the hover symbol takes the click); a dot on every mark with a selection fading the rest (that is the selection fade the bar charts already have, not Tableau's Selected).

## D151 — The Color tile opens the colour controls; Format keeps the rest

- **Chosen:** clicking **Color** on the Marks card opens the flyout with the field pills and, under them, the colour controls, as Tableau's Color button does. The flyout has up to three sections, in this order, split by a hairline and named only for screen readers (`aria-label`): **Color** (Colour scale, Steps, Colour ramp or Diverging colours, Use full colour range, **Limits**, Edit member colours; Colour by category and Reverse palette were removed by [D154](#d154--colour-by-category-and-reverse-palette-are-removed-the-colour-field-does-it)), **Opacity** (Opacity) and **Effects** (Border thickness, Border colour, Line markers). Opacity and Border thickness are progress bars (a range input drawn as a filled track with the value read out: 0–100 % in steps of 1, narrowed from 10 by [D157](#d157--opacity-steps-by-1--and-border-thickness-by-05-px); None to 3 px in steps of 0.5, widened from None / 1 / 2 / 3 px by D157), not selects; Border colour is a four-swatch picker (Muted / Ink / Surface / Accent, filled from the theme variables; the stored value stays the token), not a select; the saved values are unchanged (`markOpacity`, `markBorder` keys), and Border thickness was called Mark border. The Color field pills and the Drop Field Here row open the Color section (no section of their own above it); a table, with no controls, shows them alone. Which controls show is `colour-flyout-model.js` (`colourFlyoutGroups`): a control never appears where it would do nothing, and a table has no group at all (pills only).
- **Limits** is a closed disclosure holding the range pins (Colour from / to) of a Low → high scale or the centre of a Diverging one, as Tableau tucks Start / End / Center under Advanced.
- **Format kept** what is not colour: Line pattern, Marker size, Marker shape, Edit Sizes, Shape bins, Edit member shapes, Label and tooltip controls — until [D155](#d155--every-marks-tile-opens-its-own-controls-the-color-flyout-generalised) moved each to its own tile. `wireLineControls` takes an optional key list so Line pattern stays and Line markers moves ([D119](#d119--line-pattern-and-line-markers-on-the-marks-card), [D124](#d124--line-markers-selected-dots-only-at-the-click-selected-marks)). Include totals stays under Conditional formatting ([D122](#d122--include-totals-in-the-colour-encoding)).
- **Nothing stored changes:** every key keeps its name and shape (`format.colorScale`, `markOpacity`, `markBorder`, `lineMarkers`, `sheet.memberColors`, …), so no migration and no import change. The flyout shows the scale the last drawing resolved to ([D110](decisions-dashboards.md#d110--the-colour-scale-starts-automatic-diverging-when-the-data-crosses-zero-and-use-full-colour-range)) and refreshes when it changes.
- **Reverse palette** was shown on every chart type here and has since been removed ([D154](#d154--colour-by-category-and-reverse-palette-are-removed-the-colour-field-does-it)).
- **A commit rebuilds the flyout**, so the control that changed gets focus back (`flyFocus`, [D155](#d155--every-marks-tile-opens-its-own-controls-the-color-flyout-generalised)).
- **Format and the flyout are never open together** (opening one closes the other).
- **Left out on purpose:** Reset to Automatic (it would need the ask-once confirm of [D133](decisions-destructive-actions.md#d133--no-undo-one-confirmation-before-every-destructive-delete)), a palette list, Halo (waits on maps, [D118](#d118--the-marks-card-follows-tableau-except-where-the-app-has-no-uploads-no-maps-or-no-contrast-rule-yet)), a Tableau-style Edit Colors dialog opened from the legend, and an Opacity slider (every commit rebuilds the flyout, which would end a drag).

- **Rejected:** keeping a copy of the controls in Format (two homes for one setting).

## D154 — Colour by category and Reverse palette are removed; the Colour field does it

- **Decided:** the Color flyout loses **Colour by category** and **Reverse palette**. What colours a mark is the field dropped on Color, as in Tableau; a checkbox that did the same for the axis field was a second way to say it.
- **A bar coloured by its own axis field:** a bar whose one Colour dimension is also its one axis dimension (nothing else groups it: no second axis dimension, Detail or Size dimension, and one measure, not a calculation) draws one full-width bar per member in that member's colour, not a split of narrow bars beside empty slots. `planDims` reports it as `axisColour` and the Colour field is then grouped once, as a pie's slice field is; `renderSeries` colours the bars by member (the chart's `colorByCategory`), and member colours and **Edit member colours** work as before. Any other Colour field still splits as it did; Stacked always splits.
- **Scatter:** a Colour dimension already splits the points into a series per member, so the per-point flag is gone.
- **Removed keys:** `format.colorByDimension` and `format.paletteReverse` are no longer stored or read. A file that has either set to `true` opens with that dropped and a line in the open report ("… no longer exists — dropped"), so a sheet may look different from how it was saved; a saved `false` is ignored silently.
- **With a comparison period** the main bar is no longer one per member (the comparison bars share the axis), so the Colour field then draws nothing per bar and the chart says so in a hint.
- **What is lost:** the categorical order and the sequential / diverging ramps can no longer be flipped.
- **Code:** `colour-flyout-model.js`, `sheet-plan.js` (`planDims`), `render-cartesian.js`, `chart.js`, `store.js`, `workbook-model.js`.

## D155 — Every Marks tile opens its own controls: the Color flyout, generalised

- **Decided:** the Color flyout's layout is every Marks tile's. the Drop Field Here row is a full-width dashed-edge row under the pills that takes a dropped field ([D156](#d156--the-drop-field-here-row-takes-a-dropped-field-only-there-is-no-field-list)); the tile's controls follow in hairline-divided sections named only for screen readers; a commit rebuilds the flyout and focus returns to the control that changed. The 12 tiles: Color, Size, Label, Detail, Tooltip, Shape, Path, Angle, Filters, Dates, Drill, Pages.
- **Moved out of Format** (one home for a setting, as [D151](#d151--the-color-tile-opens-the-colour-controls-format-keeps-the-rest) ruled for colour): **Size** — Marker size, Edit Sizes; **Shape** — Marker shape, Shape bins, Edit member shapes; **Label** — Data labels, Label marks, Label position; **Tooltip** — a Text section (the text, Edit tooltip…) and a Behaviour section (Show tooltips, Command buttons, Tooltip mode); **Path** — Line style, Line pattern (a Line section); **Dates** — A fall is good, under the range (a Range section). Detail, Angle, Filters, Drill and Pages hold the slot only.
- **Stays in Format:** Number, Decimals, Dates, currency, Target, Target field, Gantt Length, the heatmap's Shape, Dual axis and its companions, Approximate, Background, Font, totals and the table look, conditional formatting, actions, Top N, Bins, Group dates, Legend, X / Y title.
- **A tile is quiet only while its flyout has nothing for the chart type.** Shape lights on a line, area or combo (Marker shape), Size on a circle heatmap (Marker size), Path on a combo (Line style, Line pattern). A pie keeps Size, Shape and Path quiet and their flyouts show the slot alone, with no empty section or stray divider. Marker shape stays on Shape rather than moving beside Line markers under Color → Effects (chosen over that, so a symbol setting lives on the symbol tile).
- **One rule for which control shows:** `marks-flyout-model.js` (`flyoutSections(tool, inputs)`, pure, with `colour-flyout-model.js` for Color); `toolbar-rules.js` reads the same answer (`controls`) for the quiet rule, so the controls and the dimming cannot disagree.
- **Nothing stored changes:** every `format.*` key, its default and its commit are as before, so no migration and no import change; a saved workbook is byte-identical.
- **Code:** `marks-flyout-model.js`, `toolbar-rules.js`, `dashboards.js` (`flyCtl`, `flySection`, `flyEditor`, `tileEditor`, `flyoutInputs`, `toolPanel`), `line-controls.js` (`lineKeysFor`), `tooltip-controls.js` (`tooltipKeysFor`), `dashboard.css` (`.ws-flyedit`). Tests: `tests/js/marks-flyout-model.test.mjs`, `tests/live/marks-flyouts-ui.mjs`.

## D156 — The Drop Field Here row takes a dropped field only; there is no field list

- **Decided:** in every Marks flyout the **Drop Field Here** row is a drop target and nothing else. The list of fields that opened beside the flyout (on hover, click or Enter), with its search box, table groups and picking, is removed for good. A field gets onto a tile by dragging it from the field pane onto the flyout's slot or onto the tile itself.
- **The row:** a full-width dashed-edge `div` (`.ws-addfield`) that reads **Drop Field Here** (no plus icon; the same label on a full one-field slot, which a drop replaces). It has no pointer cursor and no focus stop; hovering the slot only darkens its dashed edges and fills the row with `--surface-2`, and the slot highlights while a field is dragged over it.
- **Gone with the list:** the side-menu layer in `.worksheet`, its placement in `placeFly`, its open and close handlers (pointer enter and leave, click, Escape, press outside) and the `accepts` filter that only the list used. A rule a slot enforces on a drop is the slot's own and unchanged (`setPeriod` still refuses a non-date field on Dates with a message).
- **Keyboard:** the list was the only keyboard path onto a Marks tile, so a field can no longer be put on one without a pointer. Columns and Rows keep theirs: each field chip's plus button (and a double-click) adds it to its default shelf. Reopen this decision if the Marks tiles need a keyboard path.
- **Replaces:** the side-menu "Add field" of [D151](#d151--the-color-tile-opens-the-colour-controls-format-keeps-the-rest) and the list in [D155](#d155--every-marks-tile-opens-its-own-controls-the-color-flyout-generalised); the rest of both stands.
- **Nothing stored changes:** no key, default or saved file is touched.
- **Code:** `dashboards.js` (`addFieldRow`, `toolPanel`, `wireFieldDrop`), `dashboard.css` (`.ws-addfield`). Tests: `tests/live/colour-menu-ui.mjs`, `tests/live/marks-flyouts-ui.mjs`.

## D157 — Opacity steps by 1 % and Border thickness by 0.5 px

- **Chosen:** the Color flyout's two progress bars move in small steps. **Opacity** runs 0–100 % in steps of 1 (was 10); **Border thickness** runs None, then 0.5 to 3 px in steps of 0.5 (was None / 1 / 2 / 3 px). The readout still follows the thumb and the change still commits on release; the arrow keys move one step and focus stays on the bar after each commit.
- **Stored:** `format.markOpacity` is any whole percent 0–100 (older multiples of 10 are still valid, so no migration). `format.markBorder` is `none` or a px number, 0.5 to 3 in steps of 0.5; the older `thin` / `medium` / `thick` still draw as 1 / 2 / 3 px and import turns them into the number. A value off the step is reset with an issue, never rounded.
- **Rejected:** more named keys between `thin` and `thick` (a list that grows with every step); rounding an off-step number on import (rule 3: out-of-range input is rejected, not silently clamped); a finer border step than 0.5 px (a 0.25 px stroke is invisible on a 1× screen).
- **Code:** `mark-opacity-model.js` (`OPACITY_STOPS`, `markOpacityError`), `mark-style-model.js` (`MARK_BORDER_STOPS`, `markBorderError`, `borderWidthOf`, `storedBorder`), `workbook-model.js` (`sanitizeSheet`), `chart.js`, `dashboards.js` (`fmtMeter`). Tests: `tests/js/mark-opacity.test.mjs`, `tests/js/charts2.test.mjs`.
