# MySQL and ClickHouse syntax in Edit SQL

The Edit SQL dialog ([sql-editor.md](sql-editor.md)) can be written in **MySQL** or **ClickHouse** syntax. A switch in the footer picks one; **MySQL is the default**, because
many users know it, while ClickHouse is what the database speaks and what always runs ([D106](../../decisions/decisions-custom-sql.md#d106--mysql-syntax-in-edit-sql-translated-to-clickhouse)).

**Code:**

- `Canvas/sql-dialog.js` — the switch, the conversions, the panel
- `Canvas/sql-editor.js` — highlighting and Format follow the syntax
- `Features/Rows/SqlController.cs` — `POST /api/sql/translate` ([api-custom-sql.md](../../reference/api-custom-sql.md#translate))
- `ClickHouse/SqlTranslator.cs` — runs the script as a child process
- `Tools/sql_translate.py` + `Tools/vendor/sqlglot/` — the translator (sqlglot 30.31.0, MIT, pure Python)

## What you see

- **Footer switch** `MySQL | ClickHouse` (a radio group, left of Reset and Format). The chosen segment is solid ink and bold.
- **Opening a card:** the default `SELECT` reads the same in both and opens in MySQL. A saved query opens as the MySQL text it was written as; a query written in ClickHouse is translated for display, and opens in **ClickHouse** syntax with a warning when the translation would not mean the same (below), or when it can't be translated.
- **Switching** converts the text in place (the editor is read-only meanwhile). If it can't be converted the switch is undone and the reason shown ("Can't convert to MySQL syntax: …"). Highlighting (`text/x-mysql` / `text/x-clickhouse`) and Format follow the syntax.
- **ClickHouse SQL that will run** — in MySQL syntax, a read-only panel under the status line shows the translation of the current text (hidden while it is being worked out; it opens by itself when ClickHouse refuses the translation).
- **Status line:** in MySQL syntax the message is "Translating and checking with ClickHouse…", then "Valid query · N columns", or the problem. A translator parse error is underlined **in the MySQL text** at the place it names. A refusal from ClickHouse is about the *translated* query, so it is shown in words only ("ClickHouse refused the translated query: …"; its line and column belong to the other text).

## What is saved

The card **always runs ClickHouse SQL** (`customSql`, [query-sources.md](query-sources.md#custom-sql-on-a-card)). When the query was written in MySQL, that text is kept beside it as `customSqlMysql` so reopening shows exactly what was typed (workbook file, [data-model.md](../../reference/data-model.md)); a query saved in ClickHouse syntax drops it. MySQL text that is only our translation of a ClickHouse query is never recorded as written.

A round trip never rewrites a query by guesswork: the dialog remembers which MySQL and ClickHouse texts it paired, so switching back and forth, and **Save without editing**, give back exactly the original text. Only text you *edit* in MySQL is translated again.

## The round-trip check

Turning ClickHouse into MySQL and back can change a query without a trace: a case-sensitive `x = 'abc'` comes back ignoring case, a division comes back guarded against zero, `lower(x)` comes back as the UTF-8 `lowerUTF8(x)`. A ClickHouse function MySQL does not have is not shown at all (it is refused by name, below), and `count()` / `ORDER BY a` round-trip unchanged. So for a query written in ClickHouse the dialog translates it to MySQL and back, and **opens it in MySQL syntax only when all three checks pass** (`meaningKept()` in `Core/sql-roundtrip.js`, unit-tested):

1. **The translator reports no repair that changes meaning** on the way back: its answer carries `changes` — `ilike` (LIKE ignores case), `case-fold` (`=`, `!=`, `IN` against text ignore case), `div-null` (division by zero gives NULL), `nulls-first` (ORDER BY keeps MySQL's NULL order), `regexp-ci` (REGEXP ignores case), `round-half-away` (a decimal literal rounds half away from zero), `null-aware` (GREATEST / LEAST give NULL for a NULL), `bit-ops` (unsigned 64-bit arithmetic), `group-concat`, `math-null` (logarithms and roots give NULL outside their domain). A future repair added to the script is covered the moment it reports itself; form-only repairs (`DATEDIFF`, `DATE_ADD`, …) are not listed.
2. **ClickHouse accepts the round trip and returns the same columns** (names and types): a mangled function name fails here.
3. **ClickHouse reads both texts the same way:** `EXPLAIN SYNTAX` of the original and of the way back are equal after `canonSyntax()` (layout, the case of function names and `coalesce`/`ifNull` are ignored — only once ClickHouse has accepted both, which is what proves every case-sensitive name was right). This catches what 1 and 2 cannot see, such as a changed `WHERE`. If `EXPLAIN` is unavailable, 1 and 2 decide.

A false alarm only opens the query in ClickHouse syntax with "This query uses ClickHouse features MySQL doesn't have…"; a missed change would silently alter which rows it returns, so every doubt says "changed". Switching to MySQL anyway shows the conversion with "Converted as far as MySQL allows…" when it passed the translator but not these checks (a text filter, a division), or says why it cannot be shown at all ("Can't convert to MySQL syntax: toDate() is a ClickHouse function with no MySQL form"). Unchanged text is never re-translated.

**How often that happens** (`tests/live/translate-smoke.mjs`, Part 2, ClickHouse 26.8): of the **first 19 typical queries** on system tables, **8 open in MySQL syntax and 11 in ClickHouse syntax**; five date queries were added later (`formatDateTime(x, '%Y-%m')`, `'%H:%i'`, `dateDiff`, `+ INTERVAL`: all open in MySQL; `formatDateTime(x, '%M')` opens in ClickHouse syntax), so **12 of 24** in all. The breakdown below is for the first 19. Of the 11, 8 are for `changes` — 7 are genuine (a string comparison, `IN`, `LIKE` or a division, which really would behave differently once re-read as MySQL) and **1 is a known false alarm: a plain ascending `ORDER BY`** (going to MySQL, ClickHouse's NULLs-last order is kept with a `CASE WHEN … IS NULL` key, so the `NULLS FIRST` added on the way back changes nothing); 1 is for a different column name (`count()` → `COUNT()`, genuine: a worksheet field would lose its name), 1 for a refused function (`toDate`, genuine), 1 for `currentDatabase()` → `CURRENT_DATABASE()` (a **known false alarm**). The default `SELECT` of a card and any query written in MySQL syntax are not affected: they open in MySQL. Most saved ClickHouse queries that filter on text therefore open in ClickHouse syntax; whether that trade-off is right is the product's call (the alternative — opening them in MySQL and accepting that an edit would make the comparison ignore case — is a one-line change in `keepsMeaning`).

## Translator

`SqlTranslator` starts `python3 -I Tools/sql_translate.py` per request and writes the JSON request on stdin (`{ sql, from, to }`), reads one JSON answer (`{ ok, sql }` or `{ ok:false, kind, error, errors:[{ line, col, start, message }] }`) — no shell, no network, 10 s time limit, at most 4 at once, ≤ 64 KB of answer. sqlglot runs with `ErrorLevel.RAISE`, so a construct it knows it can't convert is refused instead of passed on. Its messages name its own classes, so the script rewrites the common ones into plain sentences. `-I` ignores `PYTHON*` variables and the user's site-packages, so only the vendored copy is used.

- **Repairs and refusals** (the rows above marked refused or rewritten) live in `mysql_to_clickhouse()` in `Tools/sql_translate.py`, applied only in the MySQL → ClickHouse direction: the text is tokenised (to find `||`), parsed, repaired on the syntax tree, then generated. Each has an exact-output test in `SqlTranslatorTests` (the common functions in `SqlFunctionTests`).
- **Checked on a real ClickHouse** (the test server, 26.8.36.3, 2026-11-12): `DESCRIBE TABLE (subquery)` and `EXPLAIN SYNTAX` under the app's guards; `tests/live/translate-smoke.mjs` runs **352 MySQL → ClickHouse cases** (the 106 below, then the common-function battery and its NULL / sign / case edges) (`DATEDIFF`, every `TIMESTAMPDIFF` family with both signs and month/year edges, `DATE_ADD` / `DATE_SUB` incl. column amounts and compound units, `DATE_FORMAT` with every code on a Tuesday in March and on week-year edge dates, `STR_TO_DATE`, `UNIX_TIMESTAMP`, `LAST_DAY`, the JSON forms on text, number, boolean, null, empty and missing values, `LIKE … ESCAPE`, `=` / `<>` / `IN` / `NOT IN` on text, Enum and non-text columns, division by zero, NULL order, the dropped clauses, `WITH RECURSIVE`, the refusals) and compares each result with MySQL's documented one (no MySQL server exists here); all 106 match. The same script re-runs on another ClickHouse (see [testing.md](../../how-to/testing.md)), because a different version could behave differently — it already showed `age('hour')` is wrong on this one.
- **Needs** Python 3 on the server (3.9 is installed on the build host). Without it, `POST /api/sql/translate` answers 503, the dialog switches MySQL off (the option is struck out with the reason as its tooltip) and carries on in ClickHouse syntax; nothing else changes.
- `Translate:Python` in configuration names another interpreter (default `python3`).
- The vendored library is published with the app (`Tools/**` is a `Content` item) and is never served over HTTP.
- **To upgrade sqlglot:** `pip install --target <scratch> sqlglot`, replace `Tools/vendor/sqlglot/` and its licence file, run `dotnet test --filter SqlTranslator` and `tests/live/edit-sql-ui.mjs`.

## Warnings

The translator answers `{ sql, warnings: [text], changes: [name] }`. A warning is a difference the translation cannot remove, in a plain sentence (today: text comparisons now ignore case, can be slower on very large tables because the primary key cannot be used, and accents still count as different letters; `GROUP_CONCAT` is not cut at 1024 characters; `CAST(x AS SIGNED)` of a column cuts a fraction instead of rounding; each shown once). It shows under the status line with a warning icon, only in MySQL syntax, only for the text it was made for (typing hides it until the new text is known), and **never blocks Save**. `changes` is for the browser (the round-trip check above), not shown.

## Limitations

The translator is a best effort, not a guarantee. **Always check the "ClickHouse SQL that will run" panel for anything beyond a plain SELECT.** Measured on the vendored version:

**MySQL → ClickHouse** (what runs):

| Case | What happens |
|---|---|
| Plain `SELECT`, `WHERE`, `JOIN`, `GROUP BY`, `HAVING`, `ORDER BY`, `LIMIT a, b`, `UNION`, CTEs, window functions, `IFNULL`, `IF`, `CASE`, `COUNT(DISTINCT …)`, `REGEXP`, `LIKE` | converted correctly (`LIMIT 5, 10` → `LIMIT 10 OFFSET 5`, `IFNULL` → `COALESCE`, `IF` → `CASE`, `REGEXP` → `match`, `UNION` → `UNION DISTINCT`). The first two cases were checked on the server; the rest of this table is each construct that needed work |
| `a \|\| b` | **refused**: it is `OR` in MySQL's default mode and text concatenation in ClickHouse, and either guess would be a silent wrong answer. Write `OR`, or `CONCAT(a, b)`. The refusal is underlined at the `\|\|` |
| `DATEDIFF(a, b)` | `dateDiff('day', b, a)` — a minus b in days, in the order ClickHouse takes (start, end) |
| `TIMESTAMPDIFF(unit, a, b)` | whole units, as MySQL counts them: `age('day' \| 'week' \| 'month' \| 'quarter' \| 'year', a, b)`; for hours, minutes and seconds the **elapsed seconds**: `intDiv(dateDiff('second', a, b), 3600)` (`… , 60)` for minutes, `dateDiff('second', a, b)` for seconds). `age('hour', …)` is **wrong on the test server** (ClickHouse 26.8: 10:00 → 12:30 gave 3, 10:59 → 11:01 gave -1), so it is not used. `MICROSECOND` / `FRAC_SECOND` → `dateDiff('microsecond', a, b)`; other units are refused |
| `DATE_ADD` / `DATE_SUB(d, INTERVAL n unit)`, `d ± INTERVAL n unit` | `d + INTERVAL n unit` / `d - INTERVAL n unit` with `n` a number (a quoted `'1'` becomes `1`); an **expression** as the amount (`INTERVAL col DAY`) becomes `d + toIntervalDay(col)`. A **compound unit** (`YEAR_MONTH`, `DAY_HOUR`, `DAY_MINUTE`, `DAY_SECOND`, `HOUR_MINUTE`, `HOUR_SECOND`, `MINUTE_SECOND`) is **one** interval of months or seconds, as MySQL adds it (so Feb 29 + `'1-2'` is Apr 29, not Apr 28; a short value leaves out the *leftmost* parts: `'5'` `DAY_HOUR` is 5 hours; a leading `-` negates the whole). The `*_MICROSECOND` units and a fractional amount are refused. A date-like text operand (`'2024-01-31'`) becomes `toDate` / `toDateTime` (ClickHouse refuses text in date functions); the same applies to `DATEDIFF`, `TIMESTAMPDIFF` and `LAST_DAY` |
| `LIKE` / `NOT LIKE` | `ILIKE` / `NOT ILIKE`: MySQL's default collation ignores case, ClickHouse's `LIKE` does not. `LIKE … ESCAPE 'c'` becomes the backslash escapes ClickHouse has (ClickHouse has no `ESCAPE`): `c` before `%`, `_` or itself is a literal, and a backslash that is not the escape character is doubled; a pattern or escape that is not text is refused |
| `=`, `!=`, `IN` against text with letters (`name = 'abc'`, `name IN ('a', 'b')`) | `lowerUTF8(toString(name)) = lowerUTF8('abc')`: MySQL ignores case, ClickHouse does not. `toString` makes it work for every column type (text, Enum, FixedString, LowCardinality, Nullable, numbers) and `lowerUTF8` for non-ASCII letters; NULL stays NULL. **Two columns** (`a.name = b.name`, a join on text or a `WHERE`): the translator lists each as a probe, the server has ClickHouse `DESCRIBE` the two columns (`SELECT a.name AS l, b.name AS r FROM <that SELECT's FROM and JOINs>`, no rows read, up to 6 per query) and the pair is folded the same way when **both are text** (String, FixedString, Enum, also inside Nullable / LowCardinality); numbers, dates, mixed pairs, and a probe ClickHouse cannot answer stay as written. A join with `USING (col)` is not examined. **Not rewritten** (left exactly as typed, case-sensitive in ClickHouse): a number- or date-like literal (`'123'`, `'1e5'`, `'2024-01-01T10:00:00'`), `''`, a list that is not all text, `'a' = 'B'`, a subquery, `LOWER(x) = …`, `<`, `>`, `BETWEEN`. A note says it can be slower on very large tables (the primary key cannot be used there) and accents still differ. To keep ClickHouse's exact comparison, switch to ClickHouse syntax |
| `ORDER BY a` | gets `NULLS FIRST` to keep MySQL's NULL order. The emulation MySQL needs for NULL-last (`ORDER BY CASE WHEN a IS NULL THEN 1 ELSE 0 END, a`, or `a IS NULL, a`) is turned back into ClickHouse's default `ORDER BY a` (and `… DESC, a DESC` into `a DESC NULLS FIRST`) |
| `a / b`, `a % b`, `a DIV b` | the divisor is wrapped in `nullIf(b, 0)`: division by zero is NULL, as in MySQL (ClickHouse gives `inf`, or an error for constants). Casts become `Nullable(…)` types |
| `DATE_FORMAT(d, fmt)`, `FROM_UNIXTIME(n, fmt)` | sqlglot's own output was **wrong** (found on a real ClickHouse): it rewrites the codes into another style, so `%i` (minutes) came out as `%M`, which ClickHouse reads as the **month name**, and `%W`, `%e`, `%k`, `%l`, `%M` failed. Now the MySQL codes are kept: those ClickHouse prints exactly as MySQL (`%a %b %d %e %f %H %h %I %i %j %M %m %p %S %s %T %W %w %Y %y %%`) go through `formatDateTime`, and the rest are rebuilt (`%c %k %l %D %r` with `toMonth` / `toHour` / `concat`, `%U %u %V %v %X %x` with `toWeek` / `toYearWeek`, whose modes are MySQL's `WEEK()` modes); an unknown code prints its letter, as in MySQL. A format that is not text is refused; `TIME_FORMAT` is refused (no TIME type) |
| `STR_TO_DATE(s, fmt)` | `parseDateTimeOrNull` (NULL for text that does not match, as in MySQL): a **Date** for a date-only format, a **DateTime** when it has time codes. `%r` and `%T` are rewritten; `%y` (years 70–99 read as NULL), `%D`, `%f`, `%U` `%u` `%V` `%v` `%w` `%X` `%x` are refused. A code with a separator on each side is written with the one-or-two-digit form (`%m` → `%c`, `%d` → `%e`, `%H` → `%k`, `%h` / `%I` → `%l`), so `'2024-3-5'` works as in MySQL. **Stricter than MySQL:** `%i %s %S`, and those codes when another code touches them (`'%Y%m%d'`), need zero-padded numbers — a note says so. A format with only a time is refused (MySQL answers a TIME; ClickHouse has no such type). Extra trailing text gives NULL (MySQL's behaviour there is not verified) |
| `UNIX_TIMESTAMP(x)`, `UNIX_TIMESTAMP()`, `LAST_DAY(x)` | `toUnixTimestamp(toDateTime(x))` (a Date means local midnight, as in MySQL — a bare ClickHouse Date is UTC midnight), `toUnixTimestamp(now())`, `toLastDayOfMonth(x)` (`LAST_DAY` also works unchanged as a ClickHouse alias; text dates are wrapped) |
| `JSON_UNQUOTE(JSON_EXTRACT(j, p))`, `j->>p`, `JSON_VALUE(j, p)` | one expression for all three: a JSON **text** value unquoted, any other value as its JSON text (`2`, `true`, `null`), **NULL when the key is missing**. (sqlglot's `->>` gave `''` for numbers; its `JSON_VALUE` path failed.) Paths of keys and array indexes work (`$.a.b[0]`; MySQL counts from 0, ClickHouse from 1); wildcards, slices and `JSON_VALUE … RETURNING` are refused. `JSON_EXTRACT` / `->` give the raw JSON text (`"x"`, `2`) and **NULL for a missing key** (ClickHouse's `JSONExtractRaw` alone gives `''`, which is not NULL; found in review, pinned by a smoke case); **a nested object prints without MySQL's space after the colon** (`{"k":1}`, MySQL `{"k": 1}`); **a text that is not JSON gives NULL** where MySQL raises an error |
| Common functions (`CONCAT_WS`, `UPPER` / `LOWER`, `REGEXP*`, `ROUND`, `CAST … AS SIGNED`, `GREATEST` / `LEAST`, bit operators, `GROUP_CONCAT`, `FIND_IN_SET`, `FIELD`, `ELT`, `STRCMP`, `SHA1` / `SHA2`, `DAYOFWEEK`, `WEEKDAY`, `MONTHNAME`, `DAYNAME`, `TO_DAYS`, `ADDDATE`, `SUBDATE`, `TIMESTAMP`, `TIMESTAMPADD`, `FORMAT`) | each checked on the server against MySQL's documented result (`fn:` cases in the smoke test); sqlglot's plain output was missing, wrong or silently different for all of these. `CONCAT_WS` skips NULL arguments (`arrayStringConcat(arrayFilter(…))`). `UPPER` / `LOWER` become `upperUTF8` / `lowerUTF8` (ClickHouse's own change ASCII letters only; a non-text argument is an error there). `REGEXP`, `RLIKE`, `REGEXP_LIKE`, `REGEXP_REPLACE` and `REGEXP_SUBSTR` ignore case as MySQL does: a leading `(?i)` is added (`REGEXP_LIKE(…, 'c')` stays case-sensitive; `REGEXP_REPLACE`'s `$1` becomes `\1`; `REGEXP_SUBSTR` gives NULL when nothing matches; a start position, occurrence or other match type is refused). `ROUND(2.5)` and `CAST(2.5 AS SIGNED)` of a decimal **literal** round half away from zero (MySQL's exact numbers: 3; ClickHouse's Float64 gives 2) through `toDecimal128`; a column's `CAST … AS SIGNED` cuts the fraction in ClickHouse, which a note says. `GREATEST` / `LEAST` give NULL if any argument is NULL (ClickHouse skips NULLs). `& \| ^ << >> ~` and `BIT_COUNT` become `bitAnd` … `bitCount` over `toUInt64`, MySQL's unsigned 64-bit arithmetic (`~5` is 18446744073709551610). `GROUP_CONCAT` keeps its separator (default `,`; sqlglot's output joined with nothing), `DISTINCT`, `ORDER BY` (NULL first ascending, last descending; mixed directions are refused), skips NULLs and is NULL for a group with no value, with a note that MySQL cuts it at 1024 characters and this does not. `FIND_IN_SET`, `FIELD` (with text) and `STRCMP` ignore case; `FIND_IN_SET`, `STRCMP`, `GREATEST` give NULL for a NULL argument; `ELT` gives NULL out of range. `SHA1` / `SHA2(x, 224 \| 256 \| 384 \| 512 \| 0)` are lower-case hex text. `DAYOFWEEK` (Sunday = 1) and `WEEKDAY` (Monday = 0) from `toDayOfWeek`; `MONTHNAME` / `DAYNAME` with `dateName`; `TO_DAYS` with `toRelativeDayNum` + 719528; a date text in `QUARTER`, `HOUR`, `MINUTE`, `SECOND`, `EXTRACT` becomes `toDate` / `toDateTime`; `ADDDATE`, `SUBDATE` and `TIMESTAMPADD` are `DATE_ADD` forms; `TIMESTAMP(x)` is `toDateTime(x)` (two arguments refused). **`FORMAT(n, d)` and `INSERT(s, pos, len, new)` are refused**. `LN` / `LOG` / `LOG2` / `LOG10` / `SQRT` / `ASIN` / `ACOS` are NULL outside their domain (MySQL; ClickHouse gives `-inf` / `nan`), a literal inside the domain is just the call. `LOCATE`, `INSTR` and `POSITION` ignore case (`positionCaseInsensitiveUTF8`). `BIN(n)` has no leading zeros (ClickHouse pads to whole bytes). `BIT_LENGTH(s)` is `length(s) * 8`. Functions ClickHouse does not have at all (`OCT`, `CONV`, `TIME_TO_SEC`, `SEC_TO_TIME`, `ORD`, `JSON_LENGTH`, `JSON_VALID`, `JSON_TYPE`, `JSON_CONTAINS_PATH`, …) pass through and ClickHouse answers "unknown function" (loud, the smoke test pins that) |
| `@var`, `@var := …`, `@@var` | **refused**, underlined at the variable: ClickHouse has no session variables |
| `SQL_CALC_FOUND_ROWS`, `SQL_NO_CACHE`, `HIGH_PRIORITY`, a SELECT-level `STRAIGHT_JOIN`, `USE` / `FORCE` / `IGNORE INDEX` | **dropped** — they do not change what a `SELECT` returns (no note: it would only be noise). A `STRAIGHT_JOIN` join is an `INNER JOIN` (a `CROSS JOIN` without `ON`) |
| `FOR UPDATE` / `FOR SHARE` | **dropped with a note**: ClickHouse has no row locks, and a read-only query's result is the same |
| `WITH RECURSIVE` | passed through unchanged; it **works on ClickHouse 26.8** (the smoke test has a case, so another version shows the difference) |
| Other MySQL-only features | passed through unchanged: ClickHouse may refuse them or read them differently |
| Double-quoted `"text"` | read as a string, as in MySQL (in ClickHouse it would be a name) |
| Backtick names | come out as `"name"` (valid in ClickHouse) |
| A MySQL stored routine, `INSERT`, `UPDATE`, DDL | not a `SELECT`: refused by the same guard as any custom SQL |
| Grouping, sorting and `DISTINCT` on text (MySQL treats `'A'` and `'a'` as one value, ClickHouse as two), accent-insensitivity, binary collations, implicit conversions (`'1' = 1`), `<` / `>` / `BETWEEN` on text, `ENGINE` details, MySQL's SQL modes | **not modelled**: there are no column types here to decide on, so these stay ClickHouse's behaviour, silently |

**ClickHouse → MySQL** (display only; never run on MySQL; `clickhouse_to_mysql()` in `Tools/sql_translate.py`):

- Plain SQL converts (`LIMIT n OFFSET m` is kept — MySQL accepts it; `ifNull` → `COALESCE`, `ILIKE` → `LOWER(…) LIKE LOWER(…)`, `ORDER BY a` → `ORDER BY CASE WHEN a IS NULL THEN 1 ELSE 0 END, a`, which keeps ClickHouse's NULL-last order).
- `formatDateTime(x, fmt)` → `DATE_FORMAT(x, fmt)` for the codes both print alike (sqlglot's own conversion read ClickHouse's `%M`, the month name, as minutes); a time zone argument or another code is refused.
- **Refused, with the reason shown** (the dialog then stays in ClickHouse syntax; switching by hand shows "Can't convert to MySQL syntax: …"): a function MySQL does not have (`toDate() is a ClickHouse function with no MySQL form`; the check is a list of MySQL function names, `MYSQL_FUNCTIONS`, applied to what sqlglot would print, so `TODATE(x)`, `UNIQEXACT(x)`, `EXPLODE(x)`, `TRANSFORM(…)` never appear), `toStartOf…()` / `toMonday()` (sqlglot builds date arithmetic from year 0), array access and arrays, lambdas, `{name:Type}` parameters, `LIMIT n BY`, and the ClickHouse-only words `PREWHERE`, `FINAL`, `SAMPLE`, `ARRAY JOIN`, `GLOBAL`, `SETTINGS`, `WITH TOTALS`, `WITH FILL`, `FORMAT` found outside quoted text.
- Hence the round-trip check above, and the rule that unchanged text is never re-translated.

**The feature itself:**

- Translation covers **one query** of at most 10,000 characters; two statements are refused.
- The checks run on **ClickHouse's description of the translated query**, not on MySQL: a query MySQL would reject can pass here, and one MySQL accepts can fail here. Nothing is ever run against MySQL; there is no MySQL server.
- Syntax errors inside MySQL text are found by the translator (position shown) or by ClickHouse (words only, no position).
- The instant checks (brackets, quotes, `SETTINGS`, blocked functions) apply to the text as typed in either syntax.
- Auto-format uses sql-formatter's MySQL or ClickHouse dialect; the dialects it knows differ slightly from sqlglot's.
- Needs Python 3 on the server (see above); each conversion starts a short process (about 0.1–0.4 s), so MySQL syntax adds a little delay while typing; many people editing at once queue behind four slots.
- A query written in MySQL keeps its MySQL text in the workbook; if the translator is later upgraded the stored ClickHouse query does **not** change until the card is saved again.
- A different MySQL version's dialect (5.7, 8.4, MariaDB) is not distinguished.
